# CLAUDE.md — frontend

Vue 3 + Vite SPA (TypeScript). See the repo root `CLAUDE.md` for the overall picture and `backend/CLAUDE.md` for the API.

Stack: Vue 3.5 + vue-router 5, TypeScript 6 / vue-tsc 3, **Vite 8 (Rolldown bundler)**, Element Plus 2.14 + `@element-plus/icons-vue` 2, TanStack Vue Query 5, vue-i18n 11, TipTap 3, Chart.js 4, ESLint 10 (flat config) + Prettier 3, Steiger 0.6, Orval 8. Node ≥ 20. Exact ranges live in `package.json`.

**The UI library was PrimeVue 4 until 2026-08-05; it is now Element Plus** (both it and its icon set are MIT, so the licensing ceiling that pinned PrimeVue to 4.x — PrimeVue 5's dual Community/Commercial model conflicts with this repo's **GPL-3.0** redistribution grant — no longer applies). Nothing named `prime*` should reappear anywhere.

**One dependency is deliberately held back and will keep showing up in `npm outdated` — do not "fix" it:**

- **TypeScript stays on 6.x.** TypeScript 7 is the Go-native port and ships **no programmatic compiler API** (its package `exports` map resolves `"."` to `lib/version.cjs`), which is exactly what `vue-tsc`/Volar embeds — `npm run build` and `npm run typecheck` would both break. Revisit when TS 7.1 restores the API.

## Hard rules

- **Never hand-edit `src/shared/api/generated/`** — Orval wipes it (`clean: true`). Regenerate with `npm run api:generate` after refreshing `swagger.json` from the backend.
- **Import across slices only through a slice's `index.ts`** public API; the sole deep-import exception is `@/shared/api/generated/…`. Steiger (`npm run lint:fsd`) enforces the FSD layer/import rules — **ESLint does not**.
- **All UI text goes through Vue I18n — never hardcode string literals.** Messages live centrally in `src/shared/i18n/locales/es.ts` (namespaced: `common`, `nav`, `errors`, `pages.*`, `features.*`, `entities.*`, …). Use `$t('key')` in templates, `const { t } = useI18n()` in `<script setup>`, and `i18n.global.t('key')` (from `@/shared/i18n`) outside setup — mappers, router guards, plain modules. The app is **Spanish-only** (single `es` locale); a second language is a drop-in `en.ts` next to `es.ts`. Element Plus built-ins (pagination, date picker, `ElMessageBox` defaults) are localized by its **own bundled `es` locale**, passed as `{ locale: es }` in `src/app/config/element-plus.ts` — there is no hand-maintained locale file any more.
- `@` is the only path alias (`→ ./src`).

## Commands

`npm run dev | build | typecheck | lint | lint:fix | lint:fsd | format | api:generate` — see `package.json`. There is no test suite; `build` is the only genuinely blocking gate (it runs `vue-tsc`). The dev server proxies `/api` to `VITE_API_PROXY_TARGET` (`.env.local`); the code fallback is `https://localhost:5001`, so set `http://localhost:5150` for the local backend.

## Architecture: Feature-Sliced Design

Layers under `src/` (imports flow downward only; slices in the same layer must not import each other):

- `app/` — composition root: `main.ts`, `App.vue` (picks layout from `route.meta.layout`), `config/` (`registerProviders`: Element Plus, TanStack Query), `router/` (routes centralized in `router/routes.ts`), `layouts/` (`DefaultLayout`, `AdminLayout`, `BlankLayout`).
- `pages/` — one slice per route; admin pages under `pages/admin/`.
- `widgets/` — one slice, `content-entity-page`: a reusable admin CRUD widget (table + create/update/delete/feature mutations). **The announcements admin page is its only consumer**; events, resources, partners, users and catalogs are all bespoke pages over their `manage-*` feature. Do not assume new admin pages should adopt the widget.
- `features/` — `auth`, `account`, `register`, `send-email` (the admin-only compose-and-send popup, shared by the users page and the event *Asistentes* tab), and the admin `manage-*` slices (`manage-activities`, `manage-catalogs`, `manage-events`, `manage-partners`, `manage-resources`, `manage-users`).
- `entities/` — business entities. Segments: `api/` (`requests.ts`, `mapper.ts`, `queries.ts`, `query-keys.ts`, `mutations.ts`), `model/` (types + state), `ui/` (cards). **`entities/feed/` and `entities/participation/` are dead leftovers** — empty `api/`+`model/` directories with no files, no `index.ts`, untracked by git. Not a pattern to copy or extend.
- `shared/` — `api/`, `branding/`, `config/`, `i18n/`, `lib/`, `ui/`.

Slices are **kebab-case** and each exposes a public API via `index.ts`. Four Steiger constraints are load-bearing and nothing else catches them:

- **`shared/lib/` sits at exactly the `fsd/shared-lib-grouping` threshold of 15 children**, so adding a 16th file there breaks `npm run lint:fsd`. Fold new helpers into an existing module — that is why `formatFileSize` lives in `format.ts` and `useActionConfirm` in `use-delete-confirm.ts`.
- **Do not rename `shared/branding/` back to `assets/`, or `app/config/` back to `providers/`.** `fsd/segments-by-purpose` bans both names (they describe *what the contents are*, not their purpose). `branding/` holds bundled binary assets (`logo-mark.png` for `BrandLogo`, `logo-mark-large.png` for the home hero) and still re-exports them through an `index.ts`, because Steiger requires the public API even for a binary-only segment.
- **`fsd/insignificant-slice` is deliberately off** in `steiger.config.ts` (which carries no comments) to allow single-consumer slices. It is the most commonly disabled FSD rule because it penalizes preparatory slicing; enabling it would dissolve single-consumer slices into their consumer and leave the parallel `manage-*` admin features structurally inconsistent.
- The same config ignores `**/shared/api/generated/**`, which is Orval output and does not follow FSD slicing.

## API client

- `npm run api:generate` runs Orval on the committed `swagger.json` → `src/shared/api/generated/`, split into `generated/endpoints/<tag>/<tag>.ts` (plain request fns like `getApiEvents`) and `generated/models/` (DTO types + the `ErrorCode` enum). Refresh `swagger.json` from the backend's Swagger endpoint whenever the API changes.
- Orval is set to `client: 'vue-query'`, **but the app ignores the generated `useXxx` hooks**. The pattern: each entity's `api/requests.ts` wraps the generated request fns, `api/mapper.ts` maps DTO → domain type, and hand-written composables in `api/queries.ts` / `api/mutations.ts` use TanStack Query with keys from `api/query-keys.ts`. Follow this for new endpoints on the **public** side. The admin side largely skips the wrapper: `entities/catalog`, every `manage-*` feature and most `pages/admin/*` import generated endpoint fns directly. That is the established admin pattern, not a violation to clean up.
- `src/shared/api/http-client.ts` is the Orval mutator: native `fetch`, `credentials: 'include'`, same-origin relative `/api/...` URLs. It handles CSRF transparently (fetches `/api/auth/csrf` before unsafe methods, sends `X-CSRF-TOKEN`, retries once on an invalid-token error) and throws `ApiError` (`status`, `code`, `traceId`). User-facing copy comes from the `errors.*` namespace of `es.ts` — one key per backend `ErrorCode` value — resolved by `getErrorMessage(error, fallback?)` in `src/shared/lib/api-error.ts` (falls back to `errors.generic` when the code has no key). A new backend `ErrorCode` means a new `errors.<Code>` key. Call `resetCsrfToken()` after login/logout (session requests already do).
- **The frontend never HTTP-caches `/api`**: every fetch goes out with `cache: 'no-store'` and the QueryClient uses `staleTime: 0` (always refetch on mount). Do not raise either — server-side OutputCache/HybridCache absorb the load. Images (`<img src="/api/files/{id}/content">`) revalidate on every use via ETag (`no-cache`), so a replaced file shows up immediately.
- The `@/shared/api` barrel exports `ApiError`, `resetCsrfToken`, `unwrapOrNull` (swallows the given statuses into `null`, default `[404]` — the `/api/auth/me` callers pass `[401, 403]`), `toPage`, and `FEATURED_FIRST_SORT` (`'-featured,-createdAt'`).
- **Listing rule: filtering, sorting and pagination always happen server-side.** Interactive admin tables go through `useServerTable` (`@/shared/lib`, server-driven `el-table` + `el-pagination` → query params); public growing lists go through `usePagedList` ("Cargar más" over `useInfiniteQuery`); design-bounded sets (household, minors, one event's activities, sponsors) are fetched in a single call with `pageSize: 100` and a server `sort`. Never re-filter/re-sort/slice fetched lists in components — add the missing query param to the backend instead.

## Routing & auth

- Guards are **per-route `beforeEnter`**, not global — `requireAuth`, `requireAdmin`, `redirectIfAuthenticated` in `src/features/auth/model/guards.ts`. Every admin route goes through the `adminRoute(path, name, component, meta?)` helper in `routes.ts`, which applies `requireAdmin` and defaults `meta.layout` to `'admin'`. The two print pages (event badges, event roster) use the same helper and simply override that default with `{ layout: 'blank', seo: { …, noindex: true } }` — the `...meta` spread lands after `layout: 'admin'`, so `blank` wins. All admin routes are lazy-imported.
- Session state is a **module-level singleton** (no Pinia): `src/entities/session/model/session.ts`. `useSession().resolve()` lazily calls `GET /api/auth/me` (deduped in-flight); `App.vue` bootstraps it on mount. Auth is a server-set cookie; only the theme is stored in `localStorage`.
- **`AuthUser.earlySignupEligible` mirrors two backend seed GUIDs.** `EARLY_SIGNUP_USER_TYPE_IDS` in `src/shared/config/app.constants.ts` duplicates `SeedIds.UserTypes.Member`/`.Sponsor` (Socio/Patrocinador) so the event page can enable signup during an event's early window. Nothing checks the two lists agree — the backend gate is authoritative, so a drifted constant only mis-renders the UI (the API still refuses with `ActivitySignupEarlyOnly`). Match on the id, never on the catalog `name`, which admins can edit.

## Theming & styles

- Light/dark is custom, CSS-variable driven: `:root` holds light tokens, the `.ca-dark` class on `<html>` holds dark tokens (`src/assets/styles/variables.css`, all tokens `--ca-*`). `useTheme()` (`src/shared/lib/use-theme.ts`) toggles the class and persists `localStorage['ca-theme']`. Quirk: in dark mode `--ca-orange` is remapped to cyan.
- **The pre-paint theme bootstrap is an external file, `public/theme-init.js`, loaded by `<script src="/theme-init.js">` in `index.html` — do not inline it.** It is external on purpose so the CSP served by nginx can stay `script-src 'self'` with no hash and no `'unsafe-inline'`; inlining it silently breaks the theme in production.
- **Element Plus scopes its dark variables to `html.dark`, so `useTheme()` and `public/theme-init.js` both toggle `dark` *alongside* `ca-dark`.** `ca-dark` stays the canonical project class (it is what `currentThemeFromDom()` reads and what `variables.css` keys off); `dark` exists purely to switch Element Plus. Remove either one and half the UI stays light.
- Element Plus is re-skinned by mapping `--el-*` tokens to `--ca-*` in `src/assets/styles/element-plus-overrides.css`, imported from `src/app/config/element-plus.ts` **after** `element-plus/dist/index.css` and `element-plus/theme-chalk/dark/css-vars.css`. That import order is load-bearing, and the overrides sit **outside** any `@layer`: Element Plus ships unlayered CSS, so a layered rule can never beat it.
- All component styles are `<style scoped>`; global styles live only in `src/assets/styles/` (`main.css`, `variables.css`, `element-plus-overrides.css`, `richtext.css` — the last styles rendered rich-text HTML, which is not scopeable).

## Responsive / mobile

The app is used from mobile browsers as much as from desktop. It was desktop-only until 2026-08-05; the pass that fixed it left these rules, and they are load-bearing.

- **There are exactly four width breakpoints, and they are literal px.** `480px` (extra-tight phone, use sparingly) · `640px` (**the** mobile breakpoint — everything stacks here) · `768px` (small tablet; admin-table narrow mode) · `1024px` (navigation collapse). Plus two feature queries: `(pointer: coarse)` for touch-target sizing and `(hover: hover) and (pointer: fine)` to guard hover-only reveals. **Never introduce a fifth value** — the pre-2026-08 code had nine ad-hoc ones (1100/860/760/720/680/640/620/480) and the gaps between them were themselves bugs: the public header collapsed at 720px but did not fit until ~1160px, so every tablet got a horizontally scrolling header.
- **There are deliberately no `--ca-bp-*` tokens.** A custom property is invalid in a media-query condition — `@media (max-width: var(--x))` is a parse error that silently discards the whole rule block — so a declared-but-unusable token set would only invite that bug. This list is the single source of truth. (`postcss-custom-media` was rejected rather than add a PostCSS step to the Rolldown pipeline.)
- Two tokens in `variables.css` *are* legal and carry the responsive intent: **`--ca-gutter`** (24px, redefined to 16px inside `@media (max-width: 640px)`) is the page/section side gutter — use it instead of a hardcoded `24px`; and **`--ca-tap: 44px`**, the minimum touch target.
- **`element-plus-overrides.css` carries one `@media (max-width: 640px)` block that fixes Element Plus globally** — do not re-fix any of it per component: editable fields go to 16px (**under 16px, iOS Safari zooms the page on focus and never zooms back** — the single most common mobile bug in this stack); `.el-dialog` becomes `calc(100vw - 24px)` wide, `max-height: 90dvh`, a flex column with a scrolling `.el-dialog__body`, so a dialog footer can never fall below the fold; `.el-message-box`, `.el-popper` and `.el-picker-panel` are viewport-bounded; the `el-date-picker` two-month range panel stacks into one column; `.el-pagination` wraps; `.el-button--small` grows to 36px; table horizontal scrollbars are always on. **Never set a mobile `width` on an `el-dialog`.**
- **Navigation collapses at 1024px into an `el-drawer`** in both layouts — `AppHeader.vue` (right-hand drawer: primary nav, admin/account links, login/register/logout) and `AdminLayout.vue` (left-hand drawer over `ADMIN_NAV`). Both watch `route.fullPath` to close on navigation, because `el-drawer` does not self-close. The drawer body is rendered by the layout component, so its `<style scoped>` reaches it; the `.el-drawer` shell itself is not, and is themed in `element-plus-overrides.css`.
- **`useMediaQuery(query)` lives in `shared/lib/use-theme.ts`, not in its own file** — `shared/lib/` sits at exactly the Steiger `fsd/shared-lib-grouping` cap of 15 children, so a new file there breaks `lint:fsd`. `useServerTable` uses it to switch the pagination layout to `'prev, pager, next'` (`pagerCount: 5`) under 640px, and re-exports `isNarrow` so a page can `v-if` low-value `el-table-column`s away on phones.
- **`theme-color` is a single meta tag driven by JS**, not two `prefers-color-scheme`-gated tags: the theme is a manual class toggle, so a scheme-gated tag paints the mobile browser chrome the wrong colour whenever the user's choice differs from the OS. `public/theme-init.js` sets it pre-paint and `useTheme`'s `apply()` sets it on every toggle. It stays external — the production CSP is `script-src 'self'` with no nonces.
- Use `100dvh` (with a `100vh` line before it as the fallback) for full-height layouts. On mobile `100vh` is the *expanded* viewport, so browser chrome pushes content off-screen.
- **Element Plus is registered globally** (`app.use(ElementPlus, { locale: es })`), so templates use the kebab tags (`<el-button>`, `<el-input>`, `<el-table>`) with no per-file import. Only the imperative APIs are imported explicitly, and only where used: `ElMessage`, `ElNotification`, `ElMessageBox`, `ElLoading`.

## Brand assets

- **Every image lives under `Resources/<Type>/`**, a build-time source folder that is **not** served — only `public/` and `dist/` are. Today that is `Resources/Images/` (`codigo-activo-logo.png`, the 1254×1254 transparent master, and `logo-mark-512.png`) and `Resources/Templates/` (`og.html`). Add a new resource type as a new folder beside them.
- **The derived icons are committed files with no generator behind them.** `public/favicon.ico` (16/32/48), `public/favicon-96x96.png`, `public/apple-touch-icon.png` (180×180), `src/shared/branding/logo-mark.png` (192 px) and `logo-mark-large.png` (640 px) are each maintained by hand from the master, as is `backend/src/CodigoActivo.Application/Resources/Images/logo-mark.png` (96 px) — the logo the transactional emails embed as a CID inline image, an `EmbeddedResource` compiled into the Application assembly (see `backend/CLAUDE.md`). Replacing the master means re-exporting **all six** and committing them together; nothing checks that they agree.
- **The sizing decisions are not arbitrary — keep them when you re-export.** The favicon sizes let the mark fill the whole canvas with no margin, because at 16 px a safe margin costs legibility; `apple-touch-icon.png` keeps a ~11% inset instead, since iOS applies its own rounded mask; and the three bundled copies are palette-quantized to 256 colours, which the gradients survive (mean composite error ≈1.3/255 against both theme backgrounds) at a fraction of the bytes. The 640 px variant covers the ~330 CSS px hero at 2× DPR; the 96 px email copy fills a 40 px slot at 2×, kept small because every message carries it to every recipient.
- **`public/og-image.png` is rendered from `Resources/Templates/og.html`**, because the card needs the real Space Grotesk / Hanken Grotesk webfonts. Screenshot it at 1200×630 with `deviceScaleFactor: 2` and downscale to 1200×630.
- **There is no SVG favicon.** The logo is a raster with gradients and cannot be faithfully vectorized, so `index.html` ships `favicon-96x96.png` + a multi-size `favicon.ico` instead of the `image/svg+xml` link it used to carry.
- **Every derived asset keeps the master's transparency — never composite the logo onto a plate.** This is a deliberate brand decision with a known cost: the mark's darkest speed bars are `#070D4A`, which scores **1.05:1** against the dark theme background (`#101014`), so they fade out in dark mode and on dark browser chrome. That is accepted; do not "fix" it by reintroducing a background tile. On iOS home screens the transparent `apple-touch-icon.png` is composited onto black by the OS — same trade-off, also expected. The email header is the third instance: an email client honouring `prefers-color-scheme: dark` paints the card `#1a1a1f`, so the same bars fade there too — accepted for the same reason, and why the email header pairs the mark with a text wordmark rather than relying on it alone.
- `BrandLogo` is the only component that renders the mark, from `@/shared/branding`. Unlike the old CSS 2×2 colour grid it replaced, it is a fixed-colour image and does **not** recolour with the theme. The printed badges (`pages/admin/event-badges`) and the admin sidebar deliberately keep their own text-only `</>` wordmark — they are not consumers of this asset.

## SEO

- `src/shared/lib/use-seo.ts` owns every head tag: `applyRouteSeo(to)` runs in `router.afterEach` (only when the navigation did not fail) from static `meta.seo` (`titleKey`/`descriptionKey`/`noindex`, i18n keys under `seo.*`); pages with dynamic data additionally call `useSeo(() => ({...}))` to layer title/description/image/`type`/`jsonLd` on top. Anything with `meta.layout === 'admin'` is forced `noindex` — which is why the two `layout: 'blank'` print pages declare `noindex` explicitly instead of inheriting it.
- It sets `document.title`, description, canonical (dropped when `noindex`), the `og:*`/`twitter:*` pairs and a single `<script type="application/ld+json" id="ca-jsonld">`. `index.html` only carries the static defaults for crawlers that do not run JS — since the app is client-rendered, per-route OG tags are invisible to non-JS scrapers.
- `/sitemap.xml` and `/robots.txt` are served by the **backend**; Vite (`server.proxy`) and nginx rewrite them to `/api/…`.

## Build & bundling

`vite.config.ts` sets `build.rolldownOptions.output.codeSplitting.groups`: explicit, dependency-ordered vendor chunks (`element-icons`, `element-base`, `element-table`, `element-components`, `element-plus`, `editor`, `charts`) matched by `node_modules` path regex, plus `chunkSizeWarningLimit: 700`.

The Element Plus groups are ordered most-specific → most-general on purpose. `element-base` (`utils`, `constants`, `hooks`, `directives`, `locale`, `_virtual`) is a genuine leaf: nothing in it imports `components/` at runtime. `element-components` requires a subdirectory after `components/` (`components/[^/]+/`), which deliberately excludes `components/index.mjs`, so the three barrel files fall through to the general `element-plus` group and the dependency order stays `base ← components ← table ← barrel`.

**Do not replace these path groups with a size-based split** (`maxSize`/`minSize`). A size-based split produced circular chunks: a component resolved as `undefined`, Vue fell back to `resolveComponent` by string, slots evaluated eagerly, and admin pages rendered blank in production while the dev server looked fine. Add or reorder a path group instead.

## Rich text, charts and the table kit

- Rich text is **TipTap 3** and the stored value is **serialized ProseMirror JSON**, not HTML. `src/shared/lib/richtext.ts` is the single source of extensions (`richTextExtensions()`: StarterKit, TextStyle/Color/Highlight/Underline, Link, TextAlign, tables, image) plus `parseRichText`/`serializeRichText`/`renderRichTextHtml`/`richTextExcerpt`/`isRichTextEmpty`. Authoring uses `RichTextEditor` (`@tiptap/vue-3`, toolbar image upload → `POST /api/files`); display uses `RichTextContent`, which renders `generateHTML` output through `v-html` with no editor instance. Its `Image` extension is wrapped to reject non-same-origin `src` at parse time, because the CSP is `img-src 'self' data: blob:` — pasted external images would save fine and render broken for everyone.
- Charts are Chart.js 4 via a local `BaseChart.vue` wrapper (Element Plus has no chart component), only on the admin dashboard (`src/pages/admin/dashboard/`): `model/charts.ts` builds the `ChartData`/`ChartOptions`, and `useChartTheme()` (`@/shared/lib`) reads the resolved `--ca-*` CSS variables into a `ChartPalette` that recomputes when the theme flips — canvas cannot read CSS variables itself. Never hardcode chart colours; take them from the palette.
- **Icons go through `AppIcon` (`@/shared/ui`), never a raw `<el-icon>` or a font class**: `<AppIcon name="pencil" />`, plus a `spin` prop. `name` is the legacy primeicons id without the `pi-` prefix, which is why the names look the way they do. `AppIcon.vue` maps 46 of them to `@element-plus/icons-vue` components and hand-draws the other 17 as inline SVG (text alignment, brand marks, `megaphone`, `users`, `table`, `palette`, the sort-amount pair, …) because Element Plus ships no equivalent. An unknown `name` renders nothing rather than throwing. Add a new icon **there**, not at the call site.
- Admin table controls are shared components in `@/shared/ui`: `ColumnSearch` (debounced text/number), `ColumnFilterSelect`, `ColumnFilterDate` (day range) — all `el-popover`-based, `v-model` + an `apply` event, and all three still expose `hide()` through `ColumnFilterShell`'s `defineExpose` — wired to `useServerTable`'s `filters`/`columns` map (`type: 'text' | 'number' | 'dateRange'`, with `fromParam`/`toParam` for ranges). `DataState` renders the loading/empty/error states.
- `useServerTable` returns `tableProps` (`v-bind` onto `<el-table>`), `paginationProps` (`v-bind` onto a **separate** `<el-pagination>`), `defaultSort`, and the handlers `onSortChange` / `onCurrentPageChange` / `onPageSizeChange`. Sorting is server-side, so every sortable column needs `sortable="custom"` — plain `sortable` would silently sort only the current page. `sortOrder` stays `1 | -1` internally (that is what `sortParam` encodes); Element Plus's `'ascending' | 'descending' | null` is translated at the boundary, and `null` clears the sort.
- **`el-table` fits its columns to the container, unlike the old DataTable which sized to content.** Give text columns an explicit `min-width` or they collapse and wrap mid-word; the action columns additionally use `fixed="right"` so they stay reachable when the table overflows.
- `useServerTable` also returns `filterParams` (the applied filters **without** page/pageSize/sort) and `sortParam`, and the module exports `fetchAllPages(fetchPage, params)`. Together they are how "export everything matching the current filters" and "email everyone matching the current filters" walk the whole result set. **The users table feeds them `table.filterParams`; the event *Asistentes* table does not** — its six filters (search, userTypeId, gender, activityId, roleTypeId, statusId) live outside the shared `columns` map, so `useEventAttendeesTable` (`features/manage-events/model/useEventReports.ts`) keeps its own `filterParams()` function and only borrows `table.sortParam`. Add a filter there and you must extend that function too, or the CSV export and the bulk email will target a different set than the screen shows.

## nginx (production image)

`frontend/docker/` holds `default.conf`, `security-headers.conf` and `proxy-api.conf`, and **none of them carries comments**, so every non-obvious behaviour is recorded here. Each item is a trap that silently breaks something if it is "cleaned up".

- **`add_header` is not inherited.** A location that declares any `add_header` of its own drops *all* server-level ones, so `security-headers.conf` must be re-`include`d inside every location that sets its own header (the `Cache-Control` ones). Forget it and that location serves no CSP, no HSTS, no frame options.
- **HSTS is emitted only when the request arrived over TLS.** It comes from a `map` on the forwarded protocol; an empty map value omits the header entirely, because browsers ignore HSTS on plain HTTP anyway.
- **Real client IP comes from `X-Forwarded-For`, but only when the TCP peer is private.** The documented topology puts a TLS-terminating proxy in front; without this every client would share one rate-limit bucket. **Caveat:** if the container is ever exposed *directly* to the internet, Docker's NAT still presents a private peer, so clients could spoof the header to dodge the limits — in that topology remove the `realip` directives or scope `set_real_ip_from` to the actual proxy address.
- **The credential-endpoint location (`login`, `register`, OTP verify, resend, forgot/reset) is a case-insensitive, unanchored regex on purpose**: ASP.NET routing also answers `/LOGIN` and `/login/`, and the regex must beat the `/api/` prefix location for every variant. **Never turn it into `^~`** — that skips the regex phase and silently disables the strict brute-force limiter.
- **The root SEO files (`/sitemap.xml`, `/robots.txt`) use exact-match locations**, which resolve before the regex phase, so they do not disturb the auth limiter. Inside them **the `include` must come before the `rewrite`**: `break` stops rewrite-module processing, and the included snippet's `set $upstream_api` is itself a rewrite directive, so an include placed after it never runs.
- **`proxy_pass` goes through a variable**, which defers DNS resolution to request time via the server-level `resolver`. That is what lets the web container start when `api` is down instead of failing to load its config.
- **Dotfile denial is nested inside the static location** so it cannot shadow the `/api` locations.
- **CSP notes**: `'unsafe-inline'` in `style-src` is required by Vue `:style` bindings and the styles Element Plus injects at runtime, and Google Fonts serves its font CSS from a separate origin; `blob:` in `img-src` covers thumbnail previews built with `URL.createObjectURL`. The app uses no frames, workers, media or manifest, so those directives are `'none'`. `script-src` stays `'self'` with no hashes, which is why the theme bootstrap is an external file.

## Conventions

- TypeScript is very strict (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `noUnusedLocals/Parameters`) — it rejects code that would compile in a looser project; expect it to bite.
- Composable file naming: **features** use camelCase (`useLogin.ts`); **entities and `shared/lib`** use kebab-case (`use-theme.ts`, `use-thumbnail-upload.ts`).
- **No comments in code or config** — rationale belongs in Markdown, which is why this file is as long as it is.
